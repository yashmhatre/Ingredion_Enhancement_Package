Read this first — one object stands between you and a deploy

The repo says staging is unprovisioned. The repo is out of date. Queried against the workspace on 2026-08-19, the schema exists, the catalog grant exists, and all four schema privileges are already on the staging service principal. What is missing is the volume, and only the volume.

The bundle points staging at /Volumes/ingredion_en/ingredion_stg/ext-ingredion-stg/Raw/. Until that volume exists, bundle deploy -t staging fails — deliberately, because a deploy that cannot find its own source volume should stop rather than silently read another environment's files. Creating it is Tier 3: you execute it, no agent does.

The good news is that it is two statements, not a provisioning project. The external location ext-ingredion-dev already spans the container root (abfss://ingredion@…/) under credential cred-ingredion-storage, so STG/ is already covered. No new external location and no new storage credential.

Create the staging volume

The schema and every grant are already in place — verified, not assumed. This phase is what is genuinely left: Phase A of the per-environment volumes plan, for staging only.

The two statements

-- The existing ext-ingredion-dev external location spans the container
-- root, so STG/ is already covered. Nothing new to create beneath it.
CREATE EXTERNAL VOLUME ingredion_en.ingredion_stg.`ext-ingredion-stg`
  LOCATION 'abfss://ingredion@ingredionenpkgdev.dfs.core.windows.net/STG/';

-- WRITE is required, not optional: the package archives ingested files
-- into processed/ and quarantine_files/ under the same root.
GRANT READ VOLUME, WRITE VOLUME
  ON VOLUME ingredion_en.ingredion_stg.`ext-ingredion-stg`
  TO `6ea945e0-2b4f-4746-b8f7-e7be51adc35a`;
Do not skip the WRITE VOLUME half. Today the staging SP holds READ_VOLUME and nothing else, on the dev volume. Read alone gets you a green ingestion run that then fails at archival — the files never move to processed/, and the next run re-ingests them. Grant both in the same statement so they cannot drift apart.
The volume root is STG/ and the bundle appends Raw/, resolving to abfss://…/STG/Raw/. Landing the Phase 04 fixtures creates that path; there is nothing to pre-create by hand.

Two traps that cost time on the dev run

Public DBFS root is disabled and file:/tmp is refused — only /Workspace and Volume paths are readable. And /Workspace has FUSE publish lag: files written and read in the same cell hit PATH_NOT_FOUND. Write, wait, then read.

One documentation contradiction worth settling

The 0.6.0 CHANGELOG opens with “production is running the code from before all of it”, and today's architecture review agrees. But docs/decisions/2026-08_ai_genie_architecture.md states the opposite outright: “the premise that production runs pre-0.5.0 code is false. There is no production deployment.” Both cannot hold. Settle it before the staging → main promotion, because the answer changes whether that promotion is an upgrade or a first install.
