The 26-case edge matrix, run clean

The first attempt collided: the fixture generator deliberately reuses real SAP table names (mara, kna1, vbap, …) across unrelated cases, and table_name_template only keys off the filename — so 17 different runs all wrote into one shared mara_bronze. Re-run with a per-case --table_name_template "<caseid>_{filename}_bronze" override, matching the pattern the 2026-08-20 staging run already used (ec20_kna1_bronze, ec20ctl_kna1_bronze). The first attempt's contaminated tables are left in place — dropping them needs DROP TABLE, which no agent runs — and are called out again under State left behind.

Two cases also needed a config field the first pass omitted, because a plain rerun would have only reproduced the default behavior, not the thing being proven:

  • EC-01/EC-02 needed required_columns/unique_columns set explicitly — without them there's nothing to quarantine against.
  • EC-20 needed csv_multiline: true — the #375 fix corrected the default escape handling, not the multiline default, which stays false by design.
  • EC-21 needed csv_header: false and schema_hint_ddl — with only the hint set, the reader silently consumed the first data row as a header instead of refusing.

Merge writes, including the merge+OPTIMIZE audit interaction

Two sequential merges into ec25_merge_optimize_bronze on merge_keys: ["MATNR"], one folder path, files swapped by hand between runs (archival being broken meant it wouldn't have cleared the first file on its own — see below):

  1. Batch 1 (2 rows, MATNR ...001 and ...002) → insert 2. Audit: row_count=2, rows_inserted=2, rows_updated=0.
  2. Batch 2 (...001 updated BRGEW 25.0→27.5, ...003 new) → DESCRIBE HISTORY shows an auto-OPTIMIZE committed immediately after the MERGE — the exact shape that broke the audit trail before #385. Audit row: row_count=2, rows_inserted=1, rows_updated=1 — version 2's numbers, not nulled by the OPTIMIZE commit.

Final table: 3 rows, MATNR ...001 at 27.5, ...002 untouched at 30.0, ...003 inserted at 12.0. #376/#385 hold in prod, on fresh data, with the same OPTIMIZE-adjacency shape that caused the original failure.

Two defects found

Archival silently fails in prod

archive_ingested_file tries to move a successfully-ingested file to processed/{date}/, falls back to quarantine_files/, and leaves the file in place only if both moves fail — logging a warning either way, never raising. That return value is never written to _ingestion_audit — only the per-file job-run result carries it, and nothing queries that after the fact.

Reproduced three times with fresh, single-purpose fixtures: a standalone one-record file (no processed/ or quarantine_files/ folder created at all — both the move and the fallback failed), all 26 edge-case source files, and the 100k run's own migration/ folder.

Root cause is not confirmed, but bronze_layer/README.md's grant runbook only documents GRANT USE CATALOG and per-environment schema grants — it never lists a WRITE VOLUME step. Reads succeed; only writes to the volume fail, consistent with prod-sp never having been granted WRITE VOLUME. Recommended: confirm the grant directly, and persist move_status/move_detail to _ingestion_audit so a future failure is visible without checking the volume by hand.

UC table-tag application fails on every attempt

Set a free-form tag (not a governed class.*/system.*/ai.*/sap.* key) on a fresh single-record ingestion via per_file_config_json's table_tags field:

  • Job succeeded; audit row shows tags_failed: true.
  • tag_outcome_json: {"applied":0,"failed":["...: 'WorkspaceClient' object has no attribute 'entity_tag_assignments'"]}
  • information_schema.table_tags confirms zero rows for the table.

Unlike archival, this failure is correctly surfaced in the audit trail — #64's design holds. The defect is a databricks-sdk version mismatch: the deployed SDK's WorkspaceClient doesn't expose entity_tag_assignments. Job-level tags (environment/layer on the job resource itself) are unaffected — a different mechanism. Recommended: pin or upgrade databricks-sdk in bronze_layer's dependencies, then re-run this fixture to confirm.

Scope and limits

Prod only. No GRANT, REVOKE, DROP or VACUUM was run by an agent. databricks bundle deploy -t prod was not re-run — main hasn't moved since the 100k run's deploy, so the already-deployed 0.6.0 wheel is identical to what a redeploy would produce.

Still not covered, and why:

  • Retry under real transient failure. Needs a fault-injection harness, not a fixture variation. Not built.
  • ai_metadata_prd and bronze_maintenance_prd. Neither job was run. bronze_maintenance_prd stays paused pending Tier 2 approval (it runs VACUUM).
  • Streaming / Auto Loader. The package's streaming mode only supports source_format: json (#323); multi-format Auto Loader is deferred. Not attempted.
  • XML. Still refused by approved_formats() pending Tier 2 sign-off on #336/#337.
  • Concurrency and sustained load. Explicitly deferred for this pass — needs a load-test design, not a fixture rerun.
