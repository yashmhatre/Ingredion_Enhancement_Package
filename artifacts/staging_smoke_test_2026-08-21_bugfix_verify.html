Why re-run instead of trusting the merge

A PR description says what the author intended. The 2026-08-20 run existed because a job's own return value said SUCCESS on a run that silently dropped rows — so this round checked the same way: land the exact fixture that failed before, run the deployed wheel, and read the result back out of Unity Catalog.

The discovery scope caught the first attempt

The ingestion job treats every immediate child of source_dir as one folder-as-table unit — it does not recurse further. Landing all five fixtures under one generic Raw/edge_cases_verify_bugfix/ root and running the job unscoped produced 0 unit(s) ingested, 10 skipped: every case folder sat one level too deep to be discovered. Each case below was re-run with source_dir pointed directly at its own parent, matching how the 2026-08-20 run must have been structured.

Two of the four re-tested defects — #371 and #374's EC-11 case — are cleanly fixed. #375 is fixed for what it targeted, the escape default; multiLine was never part of that fix's scope, so EC-20 needed an explicit override before it could be tested at all. #374's EC-12 case and #376 both reproduce, under conditions different from the ones the original fix addressed.

EC-12: fixed for the case #374 targeted, not for a real collision

identifiers.py's _resolve_names/_disambiguate, read on their own, correctly suffix colliding names: order_id, order_id_2, order_id_3. The deployed write for {"Order Id": "A1", "Order.Id": "B2", "order_id": "C3"} still raises the same error as before #374 shipped, three times over. 

[COLUMN_ALREADY_EXISTS] The column `order_id` already exists.
Choose another name or rename the existing column. SQLSTATE: 42711

Filed as #384

The disambiguation code path is evidently not reached for this input shape. Root-causing it needs a debugger against the deployed wheel, not another staging run — the logic that should apply is correct when read in isolation.

#376: fixed for the metric keys, not for auto-optimize racing the read

bronze_writer.py's _read_write_metrics now reads numTargetRowsMatchedUpdated / numTargetRowsInserted — the fix's actual target — and its since_version guard correctly rejects a commit older than the write. A genuine two-batch merge (insert, then a batch that both updates and inserts) still writes a NULL audit row for the second batch. DESCRIBE HISTORY shows why: 

version 3  OPTIMIZE  {"numRemovedFiles": "2", ...}
           ↑ no numTargetRows* keys — read as this run's metrics

version 2  MERGE     {"numTargetRowsMatchedUpdated": "1",
                       "numTargetRowsInserted": "1", ...}
           ↑ this run's actual write — never read

version 1  MERGE     {"numTargetRowsInserted": "2", ...}

Auto-optimize committed an OPTIMIZE immediately after the MERGE. _read_write_metrics reads .history(1) — the single latest commit at read time — and the guard against a stale read only rejects a commit older than expected, so a newer-but-wrong commit sails through.

Filed as #385 — data is correct, only the audit row is wrong

The merge itself is right: 3 rows, the matched key's BRGEW updated 25.0 → 27.5, the new key inserted. Only row_count/source_row_count come back NULL.
